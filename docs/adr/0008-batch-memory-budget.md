# ADR-0008: バッチ実行時のメモリ上限はバイト予算で管理する

- 状態: 承認
- 日付: 2026-08-09

---

## 背景

`docs/phases.md` §5.3 は Phase 2 着手時に決めるべき事項として次を挙げていた。

> **バッチ実行時のメモリ上限** — `convert()` が `QByteArray` を受ける以上、
> 同時にメモリへ載るファイル数は並列度で決まる。1000 ファイルバッチでの上限設計を
> Phase 2 のスコープに含める。

数字で見ると、放置できない。

- `ConversionSpec::maxPixels` の既定は `268'435'456`（16384 × 16384）。
  これを `ARGB32` で 1 枚保持すると **1 GiB**
- `docs/spec-core.md` §6 の既定並列度は `QThread::idealThreadCount() - 1`。
  開発機（macOS 14 / arm64）では 9。**理論上のピークは 9 GiB を超える**
- `docs/phases.md` §4 の受け入れ基準は「1000 ファイルのバッチで UI が固まらない」ことを要求する。
  固まらないだけでなく、**落ちないことが前提**である

さらに `src/core/Converter.cpp` を読むと、1 件あたりの実際のピークは
「デコード済み 1 枚」では済まない。

| 局面 | 同時に生存する画像 | 根拠 |
|---|---|---|
| 復号のみ | 1 枚 | `Converter.cpp:120` |
| アルファ合成 | **4 枚**（`image` / `normalized` / `canvas` / `convertToFormat` の戻り） | `Converter.cpp:41-56` |
| テキスト除去 | 2 枚（`source` / `stripped`） | `Converter.cpp:65-77` |
| リサイズ | 2 枚（縮小前 / 縮小後） | `Converter.cpp:136` |

**最悪はアルファ合成の 4 枚**である。

## 選択肢

### A. バイト予算セマフォ

総予算を決め、1 件ごとに見積りを確保してから実行し、終了時に返す。
予算を超える単独ジョブは全量を確保して 1 件ずつ実行する。

### B. `maxPixels` の既定を下げる

`ConversionSpec::maxPixels` の既定を 64 Mpx（256 MiB / 枚）程度へ下げ、並列度だけで抑える。
実装は最小だが `docs/spec-core.md` §2 の既定値変更を伴い、大きな画像が扱えなくなる。

### C. 適応的並列度

バッチ開始時に全ファイルの見積り最大値から並列度を決める。
予算という概念を持たずに済むが、大小が混在するバッチで無駄が大きい。

## 決定

**A を採る。`src/io/MemoryBudget` が総量 1 GiB のバイト予算を管理する。**

### 見積り式

```
estimate = 2 * fileSize + 16 * max(sourcePixels, resizeBoundPixels)
```

| 項 | 意味 |
|---|---|
| `2 * fileSize` | 入力バイト列と出力バイト列。出力は入力と同程度と仮定する |
| `16 * pixels` | 画像 4 枚 × 4 バイト/画素。**上表の最悪ケース（アルファ合成）に合わせた** |
| `max(...)` | リサイズで拡大する場合は出力側の寸法が支配的になるため、大きい方を採る |

`sourcePixels` は `QImageReader::size()` で**ヘッダだけを読んで**得る。復号はしない。

### 総量を 1 GiB とする根拠

`maxPixels` の既定 `268'435'456` px を `ARGB32` で 1 枚保持した量と一致する。
**「デコード済みの最大画像 1 枚分」を予算の単位に据える**という説明可能な基準であり、
`maxPixels` を変えたときに予算をいくつにすべきかも自動的に決まる。

## 帰結

- **`MemoryBudget` は `src/io` に置く。** core は上限を知らない。
  `convert()` の純粋性（`docs/spec-core.md` §6）を壊さない。
- **確保は RAII のガードで行う。** 早期 return・キャンセル・失敗のいずれの経路でも返る。
- **見積りが総量を超えるジョブは、総量の全部を確保して単独実行する。**
  超過分は許容する。予算の役目は「1 枚分の消費をスレッド数倍しないこと」であり、
  1 枚を諦めさせることではない。**この場合の実際のピークは予算を上回りうる**（最悪 4 GiB 前後）。
  それは `maxPixels` が許した大きさそのものであり、ADR-0002 の方針
  （確保失敗時の `std::terminate` を意図的に受け入れる）の範囲内である。
- **`QImageReader::size()` が無効を返した場合は「予算全量」を確保する。**
  寸法が分からない入力を小さいと仮定しない。安全側に倒す。
- **`FileSource` の上限（`IoError::TooLarge`）の既定は予算総量と同じ 1 GiB とする。**
  読み込むだけで予算を使い切る入力は、復号すればまず破綻する。読む前に落とす。
- **`QtConcurrent::mapped` の結果型にバイト列を載せない。**
  `QFuture<T>` は全件の結果を保持するため、1000 件分の出力バイト列がメモリに残る。
  結果は `JobOutcome`（パス・状態・理由・警告のみ）に限る。
- 予算の値は**設定 UI から変更できない**。指示書に記述が無く、停止条件 1 に該当するため。
  変更が必要になったらこの ADR を書き直す。
- 並行確保のテストは ASan / UBSan 込みで回す（`docs/phases.md` §3）。
- 係数 16 は `src/core/Converter.cpp` の**現在の実装**から導いた。
  合成やリサイズの実装を変えるときは、この係数を見直すこと。
  **見直さずに `Converter.cpp` の一時画像を増やすと、予算が静かに嘘になる。**
