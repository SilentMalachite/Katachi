# エージェント運用プロトコル

`CLAUDE.md` の「セッション手順」「停止条件」の詳細。**この文書は仕様より優先する。**
実装の巧拙より、進め方の遵守を重視する。

---

## 1. 曖昧さの解決順序

1. `CLAUDE.md` および `docs/` 配下の明示的な記述
2. `docs/adr/` の既存決定
3. 既存コードの慣習
4. Qt 公式ドキュメント
5. 一般的な C++ / Qt の慣習

1〜4 で決まらない場合は停止条件に該当する。
**5 に頼って判断した箇所は、報告の「推測で埋めた箇所」に必ず書く。**

---

## 2. 計画の粒度

計画に含めるもの。

- 触るファイル（新規 / 変更を区別）
- 追加するテストと、**その期待値**（実装後に決めない）
- 通す品質ゲート
- 「完了」と判定する条件
- 今回やらないこと（次セッション送りにするもの）

含めないもの。

- 実装コードそのもの（計画段階では書かない）
- 「必要に応じて〜する」という条件付きの記述（判断を先送りしない）

---

## 3. サブエージェント・並列調査

**使ってよい領域（調査のみ）**

- Qt API の存在・シグネチャ・Qt5 からの変更点の確認
- 追加コーデックライブラリのライセンス調査（Phase 3）
- 実行環境で実際に利用可能なフォーマットの実機確認
- 既存コードの読解・影響範囲の洗い出し

調査結果は要約ではなく、**根拠（URL、または `ファイル:行`）を付けて**返させる。

**使わない領域**

- `src/core/` の実装。コアは一貫した一つの設計判断で書く
- テストの期待値の決定

**並列調査の結論が食い違った場合、自分で統合しない。両論を併記して停止する。**

---

## 4. コンテキスト運用

- **`docs/progress/` と `docs/adr/` がこのプロジェクトの唯一の真実。** 会話履歴は失われる前提で書く。
- セッション冒頭で最新の progress を読む。読まずに実装を始めない。
- コンテキストの圧縮・要約の前に、**必ず progress へ追記する**。圧縮後は progress を読み直してから再開する。
- セッションが長くなったと判断したら、エージェント側から「ここで progress に書き出して区切りましょう」と提案してよい。むしろ推奨する。

---

## 5. 記録の書き方

### 5.1 `docs/progress/phaseN.md`（追記形式・append-only）

各エントリに書くもの。

```
日付 / 実施内容 / 変更ファイル / 追加テスト / 通した品質ゲート / 推測で埋めた箇所 / 残課題
```

**既存の記述を書き換えない。** 誤りを見つけた場合も遡って修正せず、新しい日付で訂正を追記する。

### 5.2 `docs/adr/NNNN-短い題名.md`（1 判断 1 ファイル）

背景 / 選択肢 / 決定 / 帰結 の 4 節。

Phase 1 までに必要な ADR。

| 番号 | 題名 | 内容 |
|---|---|---|
| 0001 | ui-toolkit | Qt Widgets を選ぶ理由（下記） |
| 0002 | noexcept-and-allocation | **コア層全体**の `noexcept` と確保失敗の方針（`docs/spec-core.md` §2） |

**ADR-0001 に書く根拠:** アニメーションが既定で無い / GPU・コンポジタ負荷が低い / ネイティブのアクセシビリティ API に素直に乗る / ファイル一覧 + 設定パネルという UI 形状に `QTableView` `QFormLayout` が適合する。

---

## 6. 作業の粒度

- 1 コミット = 1 つの意味のある変更。差分は最小に
- 無関係なリファクタ・整形を混ぜない
- 一度に 1 つの改善だけ。**「ついでに」を禁止**
- ファイルを新規作成する前に、既存ファイルへの追記で済まないか検討する。ファイル数を増やす方向のリファクタは提案に留める
- 1 Phase = 1 ブランチ = 1 PR。Phase をまたぐ変更を 1 コミットに混ぜない

---

## 7. 最初のセッションでやること

1. `CLAUDE.md` と `docs/` を通読し、**不明点・矛盾点・`docs/phases.md` の未解決事項を先に列挙して質問する**（実装前に）
2. 回答を得たら `docs/progress/phase0.md` を作成し、着手予定を書く
3. **Phase 0 の計画を提示し、承認を待つ**
4. 承認後、Phase 0 のみ実装する。Phase 1 に進まない
5. 報告書式に従って報告し、Phase 0 チェックリストを埋めた状態を示す
